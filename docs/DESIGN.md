# react-native-document-kit: design

`react-native-document-kit` gets files into a React Native app and
shows them: camera capture, photo library, file picking, downloading and
in-app preview, on Android and iOS, designed for slow networks.

This document explains what DocumentKit does, how it is built and why. The
[README](../README.md) covers day-to-day usage, development and publishing.

## 1. Goals and non-goals

### Goals

- **One package for every way a file enters or is viewed in the app:** in-app
  camera, OS camera (photo and video), photo library, Files app / internal
  storage, download, save to device and in-app preview.
- **Our own native code**, depending only on `react` and `react-native` from
  npm. Google's AndroidX / Media3 libraries via Gradle are allowed (see
  [decision D2](#d2-our-own-native-code-not-npm-libraries)).
- **Works on slow and unreliable networks:** retries, resume, idle timeouts,
  caching, streaming instead of downloading where possible.
- **Android and iOS behave the same from JavaScript,** even where the native
  implementations differ.
- **App-agnostic:** no app-specific code inside; theme, labels, auth headers and
  error reporting are passed in.

### Non-goals (for now)

- **Upload.** Uploading stays in the app. It may move into DocumentKit later as a native,
  background-safe upload module.
- **Compression, validation and the security scan.** These are app rules and
  stay in the app.
- **Server APIs.** DocumentKit never builds server URLs; the app passes complete
  URLs and headers.

## 2. Principles

| Principle | What it means in code |
|---|---|
| **Never reject** | Every public function resolves a discriminated union (`PickResult`, `DownloadResult`, `PreviewResult`, `SaveToDeviceResult`). Callers `switch` on `status`; nothing needs a `try`. |
| **One screen at a time** | `DocumentKitProvider` runs every camera, picker and preview through one busy guard. A second call while one is open resolves `busy`, never stacks a second screen. |
| **Files always end up in the app's cache** | Picked, captured and downloaded files are copied to `cacheDir/document-kit` (Android) or `Caches/document-kit` (iOS) before they are returned, so `content://` grants or picker temp files that expire cannot break a later upload or retry. |
| **Errors are reported, not shown** | DocumentKit never shows a raw error. Unexpected failures go to the host's `onError`; expected ones (cancel, network, HTTP) come back in the result for the app to word. |
| **New Architecture only** | TurboModules generated by React Native codegen from `src/specs`. No bridge fallbacks. |
| **No app imports** | Only `react`, `react-native`, peer libraries and DocumentKit's own files. ESLint blocks libraries DocumentKit replaced. |

## 3. Architecture

### Layers

```
App code
  │  useDocumentKit()  ·  downloadFile() / saveToDevice()  ·  openPreview()
  ▼
DocumentKitProvider (React)        one busy guard, camera modal, preview loading overlay,
  │                            labels/theme/onError from the app
  ▼
JS modules (src/)              result mapping, shared downloads, progress events
  │
  ▼
Codegen specs (src/specs)      typed TurboModule contracts
  │
  ├── Android (Kotlin)          android/src/main/java/com/documentkit
  └── iOS (Objective-C++)       ios/
```

### Native modules

| Module (spec) | Responsibility |
|---|---|
| `DocumentKitPermissions` | Camera and microphone permission status/request, including a real "blocked" state, and opening app settings. |
| `DocumentKitNetwork` | Snapshot of the connection (transport, upload estimate, metered, data saver) for recording quality. |
| `DocumentKitMediaPicker` | OS camera (photo/video), system photo library, system file picker. |
| `DocumentKitDownloader` | Downloads into the shared cache with progress events; saves files to the device; clears the cache. |
| `DocumentKitPreview` | Full-screen in-app viewers: documents and streamed video/audio. |

The in-app camera screen is React (`src/camera`) on DocumentKit's own camera
(`DocumentKitCameraView` + `DocumentKitCamera`: CameraX on Android, AVFoundation on
iOS); see [CAMERA_PLAN.md](CAMERA_PLAN.md).

### Source layout

```
src/
  core/        public types (PickResult, PickedFile…), file/mime helpers, foreground hook
  camera/      in-app camera: viewfinder, photo review, modal, permission mapping, icons
  media/       OS camera, photo library and file picker → PickResult
  download/    downloadFile, saveToDevice, clearDownloadCache (shared transfers, progress)
  preview/     openPreview, loading overlay
  provider/    DocumentKitProvider + useDocumentKit
  specs/       codegen specs, one per native module
android/src/main/java/com/documentkit/
  DocumentKit*Module.kt     one per spec
  DocumentKitPdfActivity    PDF viewer          DocumentKitMediaActivity   video/audio player
  DocumentKitFiles          copy/describe files DocumentKitDownloadCache   cache folders + LRU
  DocumentKitFileProvider   URIs for camera output and "Open with"
ios/
  DocumentKit*.mm           one per spec
  DocumentKitFileUtils      copy/convert/describe files
  DocumentKitDownloadCache  cache folders + LRU
```

## 4. Features

### 4.1 In-app camera — `openCamera()`, `capturePhoto()`, `recordVideo()`

- One full-screen camera for photos and videos. `openCamera({modes})` offers
  one or both; with both, a **Photo | Video switch** sits above the shutter.
  `capturePhoto()` and `recordVideo()` open it locked to one mode.
- Photo: viewfinder (flash, switch camera, pinch zoom) → Retake / Use Photo.
- Video: record / stop shutter, elapsed-time pill, pause / resume, torch,
  optional `maxDurationSeconds` auto-stop → review with a play button (opens
  DocumentKit's native player) → Retake / Use Video. MP4, H.264, so every server,
  browser and device can play it.
- **Quality follows the network** unless the caller sets `quality`
  (see [section 5](#5-slow-network-behaviour)):

  | Tier | When | Recording |
  |---|---|---|
  | high | Wi-Fi / Ethernet (not metered), or ≥ 10 Mbps upload estimate | 1080p, normal bitrate |
  | medium | 4G / 5G, metered Wi-Fi, unknown, or 2–10 Mbps upload | 720p, low bitrate |
  | low | 3G / 2G, < 2 Mbps upload, data saver / Low Data Mode, or offline | 480p, extra-low bitrate |

  Android uses the OS upload-speed estimate when it has one; iOS has none, so
  it uses Wi-Fi vs cellular, the cellular generation and Low Data Mode. Photos
  always keep the device's full resolution.
- **Microphone** is asked for when video is offered. If refused, video records
  without sound and the screen says so.
- Resolves a `PickedFile` with `source: 'camera_photo'` or `'camera_video'`
  (with `durationMs`).
- Hosted once by `DocumentKitProvider`, not once per form field.
- The switch-camera button only appears when the other camera exists.
- No camera device → resolves `unavailable`; the app falls back to
  `capturePhotoWithSystemCamera()`.
- DocumentKit's own camera, with lens pills, swipe between modes, flash auto,
  icons that turn with the phone, and optional multi-capture (`maxFiles`).
  Icons are bundled PNGs. Not device-tested yet; iOS not built in Xcode yet
  ([CAMERA_PLAN.md](CAMERA_PLAN.md)).

### 4.2 OS camera — `capturePhotoWithSystemCamera()`, `recordVideoWithSystemCamera()`

Fallback when the in-app camera reports no usable camera device.

| | Android | iOS |
|---|---|---|
| How | `ACTION_IMAGE_CAPTURE` / `ACTION_VIDEO_CAPTURE`, writing to a `DocumentKitFileProvider` URI | `UIImagePickerController` (camera source) |
| Video format | MP4 from the camera app | `.mov` re-wrapped to MP4 with `AVAssetExportSession` passthrough (no re-encode) |
| Options | `quality` (the intent only knows low/high), `maxDurationSeconds` | `quality` low/medium/high, `maxDurationSeconds` |
| Quirk handled | Some camera apps ignore the output URI and return their own; DocumentKit copies it | — |

Camera permission is checked first on both platforms (Android requires it once
the manifest declares `CAMERA`).

### 4.3 Photo library — `pickFromLibrary()`

| | Android | iOS |
|---|---|---|
| Picker | System Photo Picker (`ACTION_PICK_IMAGES`) on Android 13+, or 11–12 with SDK extension 2; `ACTION_GET_CONTENT` below that | `PHPickerViewController` |
| Permission | None | None (the picker is created without a photo library) |
| Formats | As stored | `preferredAssetRepresentationMode = compatible`; HEIC/HEIF converted to JPEG with ImageIO; video re-wrapped to MP4 |
| Limits | `selectionLimit` (0 = no limit); `ACTION_GET_CONTENT` cannot enforce it, so DocumentKit trims | `selectionLimit` |

### 4.4 Files / internal storage — `pickDocuments()`

| | Android | iOS |
|---|---|---|
| Picker | `ACTION_OPEN_DOCUMENT` | `UIDocumentPickerViewController(forOpeningContentTypes:asCopy:)` |
| Cloud files | Virtual files (e.g. Google Docs in Drive) have no bytes of their own; DocumentKit exports them in the provider's first streamable type (usually PDF) and names them to match | `asCopy: true` makes iOS download iCloud files and hand over a copy |
| Filters | MIME types, wildcards allowed (`image/*`) | MIME types mapped to `UTType`s; unknown or empty → any file |

The original file name is kept, in a per-pick folder so names never collide.

### 4.5 Permissions

- Camera, and the microphone for video (optional: video records without sound
  when refused). The library and file pickers need none on either platform.
- Android has no "blocked" status of its own. DocumentKit treats the permission as
  blocked when it has asked before and the OS no longer wants a rationale
  shown. This replaces the app's old AsyncStorage denied-count logic for the camera.
- iOS: anything other than not-determined or authorized can only change in
  Settings, so it is "blocked".
- `openAppSettings()` opens the app's settings page.

### 4.6 Download and cache — `downloadFile()`

```
downloadFile({url, fileName, cacheKey, headers, onProgress, signal})
  → cache hit?  yes → resolve from cache, no request
                no  → HTTP with Range resume → .part → final file → trim cache
```

- **Cache:** `…/document-kit/downloads/<sha-256 of cacheKey>/<file name>`, capped at
  200 MB, least recently used entries removed first. Same key → no request.
- **Resume:** an unfinished download keeps its `.part` file. The next attempt
  sends `Range: bytes=<n>-`; a 206 appends, a 200 starts over, a 416 discards
  the stale part.
- **Retries:** up to 4 attempts with 1s / 2s / 4s backoff, for network errors,
  408, 429 and 5xx. Other HTTP errors fail at once with the status.
- **Idle timeout:** 60 seconds without data, not a fixed total, so a slow but
  moving download never times out.
- **Progress:** native events (codegen `EventEmitter`), at most every 250 ms.
- **Shared transfers:** callers asking for the same `cacheKey` at once share
  one native download; each gets progress. Aborting resolves that caller as
  `cancelled` immediately; the transfer stops when no caller is left.
- **Cache file names have no spaces or path characters,** because viewers use
  the path directly. The user-visible name is passed separately when saving.
- `clearDownloadCache()` empties the cache.

| | Android | iOS |
|---|---|---|
| Transport | `HttpURLConnection`, 3 parallel downloads | `NSURLSession` data tasks with a delegate writing to the `.part` file |

### 4.7 Save to device — `saveToDevice()`

| | Android | iOS |
|---|---|---|
| Where | `Download/<subdirectory>` through MediaStore (no permission; visible in the system Downloads app; duplicates get `(1)`) | The **Save to Files** sheet; the user chooses the folder |
| Name | The name passed in | A temporary copy with the name passed in is exported, then deleted |
| Cancel | — | Closing the sheet resolves `cancelled` |

### 4.7a Download notifications (Android)

Pass the same `notification` (with one `tag`) to `downloadFile` and
`saveToDevice`:

- **While downloading:** a silent "Downloading…" notification with a progress
  bar, updated at most once a second (Android rate-limits updates). Removed if
  the download fails or is cancelled. Cache hits skip it.
- **After saving:** "Downloaded · <name>" replaces it (with a picture preview for
  images). Tapping opens the saved file directly, with no intermediate screen
  (Android 12+ rule): PDFs in DocumentKit's PDF viewer (works even if the app was
  killed), other types through "Open with".
- **One channel,** `documentkit_downloads`, named by the app ("Downloads").
- **Permission:** `POST_NOTIFICATIONS` on Android 13+, asked the first time a
  download wants a notification; older Android follows the app's notification
  setting. Refused → the download still works, without notifications.
- **iOS posts nothing:** the Save to Files sheet and the app's own message
  already confirm a save the user just made.

### 4.8 In-app preview — `openPreview()`

```
openPreview({uri, name, mimeType?, headers?, cacheKey?})
  video/audio → native player, streamed (no download)
  everything else
    remote → downloadFile into the private cache (overlay with progress + Cancel)
    local  → used as is
    → native viewer
```

| Type | Android | iOS |
|---|---|---|
| PDF | DocumentKit's own viewer on `PdfRenderer` (`DocumentKitPdfActivity`) | QuickLook |
| Images | DocumentKit's own viewer (`DocumentKitImageActivity`): `ImageDecoder` at about 2× screen size (no full-size bitmap, so no memory crash), EXIF orientation, HEIC/WebP, animated GIF/WebP; pinch / double-tap zoom to 4×, pan. SVG goes to "Open with". | QuickLook |
| Video / audio | Media3 ExoPlayer (`DocumentKitMediaActivity`), streamed with every request header | `AVPlayerViewController`, streamed; the `Cookie` header is passed as cookies (`AVURLAssetHTTPCookiesKey`) |
| Plain text, CSV / TSV | DocumentKit's own viewer (`DocumentKitTextActivity`): wrapped lines; CSV as a table with a fixed header, separator detected (comma, semicolon, tab), quoted fields supported. UTF-8/UTF-16 (byte-order mark) or Windows-1252. Files over 5 MB show their beginning with a note. | QuickLook |
| HTML | DocumentKit's own viewer (`DocumentKitHtmlActivity`), locked down: JavaScript off, network loads blocked, no file/content access, links never navigate inside it (http/https open the browser on tap). Static content only. | QuickLook |
| Office, iWork | "Open with" another app | QuickLook, in-app |
| Nothing can open it | `unsupported` | `unsupported` |

**Android PDF viewer.** Continuous vertical scroll. Pinch and double-tap zoom
from 1× to 3×; zooming re-lays the pages out and re-renders them at the new
width, so text stays sharp, with sideways scroll when zoomed. Only visible
pages are rendered, on one thread (`PdfRenderer` allows one open page at a
time), and kept in an LRU cache of about a sixth of the app's memory. Bitmaps
are capped at 2048 px wide. Page indicator "3 / 12". Password-protected or
corrupt PDFs fail with `E_VIEWER`.

**Save button (Android).** `openPreview(source, {save: {subdirectory, notification}})`
adds a Save button to the image, PDF, text and HTML viewers. It copies the shown file to
Download/<subdirectory> without leaving the viewer, confirms with a toast and
the "Downloaded" notification. iOS QuickLook's own share button already offers
Save to Files.

**Loading overlay.** `useDocumentKit().openPreview()` shows a small overlay (file
name, progress bar, Cancel) only while a download is actually running; cached
files open with no flash. On iOS the overlay must finish closing before the
viewer is presented, so DocumentKit waits for its `onDismiss` (with a 700 ms
fallback).

## 5. Slow-network behaviour

| Situation | What DocumentKit does |
|---|---|
| Large photo on a slow link | The app's existing network-aware compression still runs after the pick; DocumentKit keeps photos at the camera's size |
| Video on a slow link | Recorded at 480p extra-low bitrate (or 720p low on 4G), so there is far less to upload |
| Connection drops mid-download | Retries with backoff and resumes from the bytes already received (if the server supports `Range`) |
| Very slow but steady download | Never times out while data keeps arriving (60 s idle timeout) |
| Same document opened twice | Second open comes from the cache, offline |
| Preview, then Download (or the reverse) | Same `cacheKey`, so the second one needs no request |
| Video preview | Streams; playback starts before the file is complete; no download |
| User gives up | Cancel stops the transfer; the partial file stays so a later attempt resumes |
| Cloud-only picked files | iOS downloads iCloud files as part of the pick; Android exports virtual files |

## 6. Host apps

DocumentKit has no app-specific code. A host app mounts `DocumentKitProvider`
with its theme, translated labels and error reporting, and passes complete URLs,
headers and cache keys. Each app documents its own integration (which screens
use which call, cache-key scheme, translations) in its own repository.

## 7. Decisions

Dates are when the decision was made (October 2026).

#### D1. An open-source package, `react-native-document-kit`
Built first inside a production app, then extracted as
an independent, MIT-licensed package on npm, so any React Native app can use it
and the first app depends on it like any other.

#### D2. Our own native code, not npm libraries
Goal: depend only on `react` and `react-native` from npm. Google's Android
libraries via Gradle (AndroidX core, ExifInterface, RecyclerView, Media3, and
CameraX when the camera is rewritten) are accepted; they are platform-level and
most are already in the app. Trade-off: DocumentKit owns the platform edge cases
(device-specific camera apps, orientation, picker quirks).

#### D3. New Architecture only
The app runs with `newArchEnabled=true`, and React Native 0.82+ has no legacy
architecture. Supporting only TurboModules keeps the native code small.

#### D4. Results, not exceptions
Every public call resolves a union with `status`. Pickers and viewers are user
flows where "cancelled", "busy" and "permission denied" are normal outcomes,
not errors.

#### D5. Copy every file into the app's cache
`content://` grants and picker temp files can disappear before the upload or a
retry. Copying once, at pick time, makes every later step reliable.

#### D6. iOS photo library and file picker ask for no permission
`PHPickerViewController` and the document picker need none. The app's old
photo-library prompt only blocked users who said no.

#### D7. Save to device: MediaStore on Android, Save to Files sheet on iOS
iOS files used to go to a Documents folder the Files app could not see. The
Save to Files sheet lets the user choose a visible folder without Info.plist
changes. Android's MediaStore Downloads needs no permission on API 29+.

#### D8. One cache for preview and download
Keyed by account + document id, so a file fetched once is reused for both and
opens offline. Assumes a document id always means the same content (see open
questions).

#### D9. Preview stays inside the app
Video and audio stream into a native player; documents download silently into
the private cache and open in a native viewer. Researched: QuickLook needs a
local file; Media3 and AVPlayer stream with auth; PDF.js could stream PDFs
with range requests but adds about 2 MB of bundled JavaScript and needs server
`Range` support. **Chosen: native viewers with silent caching.**

#### D10. Android PDF: our own viewer on `PdfRenderer`, not Jetpack PDF
`androidx.pdf` 1.0.0-beta01 (August 2026) has search and selection, but needs
the app to compile against SDK extension 19 (new SDK platform on every machine
and CI, plus a build change) and brings in Jetpack Compose. **Chosen:** the
platform `PdfRenderer` with DocumentKit's own viewer: no new dependency, no build
change; no text search or selection in the first version.

#### D11. Android Office files: "Open with" another app
Android has no built-in Office renderer. Options were server-side conversion
to PDF (needs backend), bundled JavaScript renderers (approximate layout, no
PowerPoint) or "Open with". **Chosen: "Open with"** for now. Microsoft's online
viewer was ruled out because it sends files to Microsoft.

#### D12. Cache file names without spaces
The old preview code stripped spaces because viewers use the path directly.
Cache names are internal; the user-visible name is passed when saving.

#### D13. Video recorded in-app, quality from the network
Video used to open the phone's camera app (inherited from image-picker). It now
records in DocumentKit's camera, like photos, with a Photo / Video switch (chosen
over hold-to-record, which is hidden and harder with screen readers). Quality
follows the network rather than a fixed setting, so slow connections get small
files. H.264 over H.265: H.265 is up to 50% smaller but not every server or
browser plays it. Refused microphone → record without sound rather than block.

#### D14. Download notifications: native on Android, none on iOS
The old notifee notification created a new channel per download and
re-registered its tap listeners on every call, and kept a third-party library
in the app for one notification. (`POST_NOTIFICATIONS` was already declared by
Firebase Messaging and notifee's own manifests; DocumentKit now declares it too.) DocumentKit posts its own with
`NotificationCompat` and one channel; tapping opens the file directly, PDFs in
DocumentKit's viewer. Android's `DownloadManager` was considered (system
notification, no permission) but bypasses DocumentKit's cache and can't open the
in-app viewer. iOS posts nothing for a save the user just confirmed in the Save
to Files sheet; a local notification belongs with future background downloads,
behind a forwarding notification delegate so DocumentKit never takes over the app's.

   `takePhoto`, replacing `react-native-vision-camera`, `react-native-blob-util`

4. **Upload module** (later): background-safe, resumable, using the same
   result style.
5. **First publish** of `0.1.0` to npm.

## 9. Open questions

Questions about a particular server (whether it answers `Range` requests, when
a cached document can change) belong to the host app: they decide how it sets
`cacheKey` and whether resumed downloads help.

## 10. Known limitations

- **Android process death:** if Android kills the app while the OS camera or a
  system picker is open, the pending result is lost and the user picks again.
- **Android PDF viewer:** no text search or selection; zoom capped at 3×; bitmaps capped at 2048 px wide.
- **Android Office files** open in another app, not in DocumentKit.
- **iOS video auth** sends only cookies. A developer forum report says cookies passed this way can be
  missing on player retries; this still needs testing.
- **Video on Android** has only two quality levels through the camera intent.
- **Partial downloads** resume only when the server supports `Range`.
